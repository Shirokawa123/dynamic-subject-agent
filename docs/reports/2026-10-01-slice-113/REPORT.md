# S113：减少本地等待，保留失败原因，完成回复候选

2026-10-01。本轮已实际改代码并完成离线验证，产品模型调用和凭据读取均为0。没有使用S112余20次、替换用户服务或改写S112真实失败。人物回复是否更自然仍未实测，不能宣布A/B已经修好。

## 已改善的部分

**本地等待减少。** 剖析发现同一个权限操作会嵌套多次读取/验证同一身份。本次把策略和授权快照核对放到一次已验证读取内；下一次发送、模型返回及最终提交仍重新读取，没有跨轮缓存、跳过完整性或降低落盘保证。

同一原创建角种子、同一纸船前三轮、同一个Facade及本地transport对照：

| 观察 | 修改前 | 修改后 |
| --- | --- | --- |
| 三轮完整身份读取（profiler） | 45次 | 12次 |
| 不开profiler的三轮耗时 | 1.814 / 1.888 / 1.962秒 | 1.029 / 0.972 / 1.013秒 |
| 中位数 | 1.888秒 | 1.013秒 |
| 完整提交/冷重开历史 | 通过 | 通过 |

这组本地小样本中位数下降约46%。数据见[耗时原始记录](local-latency.json)，机制与原始profile定位见[诊断依据](../../research/2026-10-01-s113-local-latency.md)。这是E盘离线测量，不能换算成S112真API/C盘用户端同幅提速；仍有Timeline完整历史重复读取成本，本片未扩大处理。

**失败原因更清楚。** S112的57个空格现在离线识别为`response-content-empty`；非空坏JSON、截断仍分别归类。网络错误仅按实际异常类型/errno区分DNS、TLS证书/TLS、连接拒绝/不可达、重置/中止或断管，未知仍保留泛化错误。原异常文字、地址、header、key和隐藏推理不进入诊断，默认ProviderFailure code和0重试保持。见[红→绿重放与一手来源](../../research/2026-10-01-s113-provider-failures.md)。

这修好了信息丢失，不是已经修好网络或服务端空白；S112旧两次网络失败缺少类型/errno，具体原因仍未知，没有被补写成DNS或其他猜测。

## 回复候选已经具体可审

[候选代码](../../../src/dynamic_subject_agent/first_life_reply_candidate.py)只生成离线请求预览，没有发送器、激活、额度或新Gateway任务。S111/S112旧policy、wire、资格和记录保持原样。

五份S112实际失败输入形成[新旧请求比较包](../../experiments/s113/reply-candidate.json)。候选把人物背景、活动依据、既往原话、当前消息分开，并把重复策略集中到一份system；所有非policy材料的完整值、事实/信念与时点限定、speaker/kind、顺序、历史开关和生活三字段逐项保留。重置后的空历史继续为空，第8步仍保留第7步实际错误原话，不暗中换成理想答案。

候选重点是“旧话错了就修正说法，不补造中间经过”和“活动用于约束判断，当前消息决定此刻话题”。不加书/台灯等关键词黑名单、不预写人物标准答案、不增加模型自评。五份请求约由12.2–15.1KB减至6.1–6.8KB；体积变小只是结构事实，不证明语言效果更好。研究依据与未采用路线见[交流修复研究](../../research/2026-10-01-s113-dialogue-repair.md)。

比较包规范摘要：`38d0a145d01df525d6fbec3fa2a852a2b2db12a1bd4996fffc158f2b59ed23ea`。源报告按规范JSON与自身evidence_digest核对，避免正常Git换行转换破坏校验；真正Provider请求仍逐字节核对。
