## 执行规则

目标是在质量达标的前提下降低**完成任务的总消耗**，包括主窗口协调、子任务、返工和检查；不追求开更多agent，也不把最低token数量当唯一目标。

| 工作 | 默认模型/思考 | 选择理由与升级条件 |
| --- | --- | --- |
| 总目标、任务拆解、架构取舍、重大冲突、最终接纳 | 当前Astra主窗口 | 保持产品上下文。主要读简报、关键差异与证据，不重新独立做完整个子任务；复杂问题由主窗口集中判断 |
| 单条查找、列文件、运行已确定检查、格式整理 | 主窗口直接用工具 | 派发说明和回收结果可能比实际工作还贵；确定性操作不用额外模型推理 |
| 有界源码定位、资料事实核查、整理已有结果 | Luna medium | 先找直接证据；跨多处关联时high，遇相互冲突的解释或关键未知转Sol |
| 范围很清楚、低风险、容易验证的局部实现 | Luna high | 让便宜模型完成完整结果。输入充分且确实需要多步细推才用xhigh，不以更高档替代缺失规格 |
| 新业务行为、多文件联动、状态/权限/恢复逻辑 | Sol high | 本项目主要实现默认走此档；不先让Luna试错一遍再重复付费。重大接口取舍先回Astra |
| 有实质风险的代码复核 | 新上下文Sol high | 检查规格与差异，不继承实施者的全部解释。简单文档/链接可由工具或Luna high核对 |
| 难以定位的失败、证据相互矛盾 | Astra判断后定向Sol xhigh或主窗口解决 | 先判断缺信息还是推理不足；同一假设一次修正后仍无新证据，应交还定位，不循环盲试 |

这是工作假设，不是模型能力排行榜。连续几次低风险任务证明Luna能稳定一次通过，再扩大其范围；语义/状态类反例多就前移Sol。官方把高思考档用于困难推理，并说明更高档会增加延迟与token；因此Luna xhigh保留按需使用。[官方说明](https://learn.chatgpt.com/docs/agent-configuration/subagents)

主窗口的模型/思考设置由当前客户端控制；本会话派发工具能够直接指定子agent的`model`与`reasoning_effort`，不能据此声称已修改主窗口档位。主窗口需要降低日常消耗时，优先减少重复阅读与不必要调度。

## 最小团队与上下文

1. Astra明确一个用户结果和验收，确认主窗口直接做还是委派值得。一次有界任务默认一个子agent，互不依赖且各有可交付结果时才同时派两个；当前工具总并发上限是4，包含主窗口，不把可用名额当配额。
2. 子agent默认`fork_turns="none"`，只给任务卡和必要路径。执行任务确需近期决定时使用最少的正数轮数；当前工具全历史fork不接受模型覆盖，不能一边全历史继承一边声称切到便宜模型。
3. 委派前指定写入文件或职责的唯一所有者。调查/复核按任务约束只读；在当前共享、无沙箱隔离环境中这不是OS强制权限。重叠写入顺序执行，主窗口不在子agent工作时改它拥有的文件。
4. 由主窗口统一派发；子agent把范围变化/需协作问题交还，不自行扩散委派。接续同一任务复用原子agent；新独立复核使用新上下文。
5. 完成后返回短结论、实际产物、检查证据和剩余问题。Astra看关键源文件/差异和证据后接纳，按风险决定是否增加独立复核。
6. 同一最终差异只运行必要检查；后续有修改或新风险才重跑相关项。提交/推送由主窗口完成，只有一张执行任务书。

### 任务卡（一般约300–800字，按需要而非硬限额）

```text
用户结果：本次要交付什么，成功如何观察。
任务：一个明确问题或完整可验证结果。
依据：必要文件/章节/来源、已确认决定及当前基线。
范围：可改文件与唯一所有者；相关数据/Provider限制。
验收：应证明的行为和必要检查，现有失败证据。
交还条件：跨职责取舍、证据冲突或一次修正仍无进展。
返回：结论；产物/行号；检查结果；未决项。避免大段日志。
```

任务卡给依据和约束，不强塞未经证实的诊断。子agent仍须读取实际适用的AGENTS/必要契约；短上下文不解除规则。初始简报保持紧凑，缺资料时定向读取，而非复制所有研究、全部历史和完整日志。

## 在本项目P1中的用法

P1要让连贯人物认识和相关经历真正进入回复路径，保留平铺基线。

1. **Astra**定用户结果、验收与写入范围，选择哪些语义判断必须保持原契约。
2. 如果现有代码证据已足够，直接交**Sol high**实施一个完整有界改动；不为凑流程另派Explorer。确有定位疑问时，先让**Luna medium/high**回答特定调用链或数据使用问题。
3. 实施期间可并行让**Luna high**根据已经确定的契约整理未见验收情景，只写指定测试/资料文件；如果情景依赖尚未定的接口，则先串行完成设计。
4. 差异稳定后，**新Sol high**核查关键知情边界、预算截断、失败与旧能力回归；Astra处理争议、看关键证据并统一提交。

通常同时只有主窗口和一个工作者；真正独立的调查/验收准备才用第三位。代码复核是完成后的顺序步骤，不让reviewer检查仍被改写的文件。对纯文档小修跳过整条流程。

## 费用与效果如何衡量

截至2026-09-26，官方Standard API短上下文每百万输入/输出token：Astra为$10/$50、Sol为$2/$10、Luna为$0.10/$0.50；同类token的单价比例约100:20:1。[API价格](https://developers.openai.com/api/docs/pricing)

Codex Standard credit表相同比例，但订阅内含额度不能只按credit表推算；模型、上下文、推理、工具及缓存都会影响实际用量。当前工具的子agent服务档位由宿主提供，不能宣称已改成Standard或自行强行换档。比较成本要记录实际tier。[Codex用量与credit](https://learn.chatgpt.com/docs/pricing)

真正比较的是：

`总消耗 = Astra拆解/接纳 + 各子任务的输入/输出/推理 + 返工 + 必要复核`

便宜子agent多输出一些token未必更贵；主窗口完整重做、复制长历史或多轮重试则可能抵消节约。并行主要改善等待时间，增加agent不自动减少token。不能承诺固定节省比例。

后续在正常开发中先记录3–5个自然发生的可比有界任务：选用模型/档位、可得的输入/缓存/输出用量、实际tier、一次通过与返工、完成时间、最终缺陷。小样本只用于调整路由，不能当严格基准；不为测费用重复实现生产功能，不额外调用项目Provider。

若日志给出output及reasoning分项，先核对是否包含关系，避免重复相加；缓存输入同样不能既算普通输入又重复计费。数据拿不到就记未知，用量与账单分别标示。上游用量脚本需要本地会话日志，正式使用前核对其任务范围与字段，只读当前获准任务树，不默认扫描无关会话或把内容外发。

已核查的[上游用量脚本](https://github.com/oil-oil/codex-team-mode/blob/ffe63d5dc93ccec4ab8d9c779757dd46a551ff49/skills/team-mode/scripts/usage_by_model.py)按内置Standard费率估算credits，不能作为混合Fast用量的准确账单；临时/远端缺失日志无法完整覆盖，按天筛选还需注意会话创建时间。可以借它观察模型分工，账户额度/实际扣费仍以官方用量界面为准。本轮未执行该脚本。
