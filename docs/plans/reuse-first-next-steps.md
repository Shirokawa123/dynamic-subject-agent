# 从局部修复转向可连续推进的对话

本文件是建议，不是执行任务书。依据独立自然验收及Slice-37结果：自然目标操作、澄清后的短答仍未完成；自然写作已改善，用户明确保留的历史控制仍生效。测试通过不代表任意自然对话可靠。

## 下一优先项：完成一次澄清闭环

建议先支持一个可体验场景：系统明确询问某一场景偏好是补充还是替换，用户回答“是补充”，系统核对待确认内容后完成一次正确写入，并允许取消。先把这个流程做完整，再用于其他目标操作，不先建设通用工作流平台。

需先设计清楚：待确认问题、所属身份、场景、候选内容及依据、允许选择、过期/取消/换话题条件；恢复时重新检查目标仍活跃、权限仍有效、问题没有被其他轮次替换。用户短答只能回答明确待确认的问题，不能作为任意状态变更的许可。

### 已核实的借鉴点

- [Rasa Flow Steps](https://rasa.com/docs/reference/primitives/flow-steps/) 的collect步骤等待特定信息，槽位校验失败时继续收集，并定义流程结束后的清理行为。可借鉴“问题有明确归属、回答有明确字段、完成后清理”的机制。不是建议把我们的所有聊天变成表单；这些文档涉及Rasa当前产品能力，直接复用前需另核许可证与部署条件。
- [LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts) 展示持久化暂停与恢复的实现思路。可借鉴恢复语义和重入处理；我们已有单Timeline及原子Publication，是否需要额外框架必须由集成比较决定，不能直接叠加第二套状态权威。

本次核实日期2026-09-13。以上是机制层参考，尚未决定引入依赖或复制源码。

## 后续顺序

1. 设计并验收一个偏好澄清闭环：确认、取消、歧义、换话题、重启、目标已变及重复回答。界面短答与最终状态同时核对。
2. 再解决自然目标操作：借鉴成熟系统如何把表达转换为结构化操作建议，继续由Python检查证据、目标和权限。对照现有ModelGateway分类接缝，优先复用；若需要调整提示或授权，先明确具体差异。
3. 最后评估更通用的记忆组织：由真实跨场景/冲突问题证明需要后，再研究时态关系、检索排序或第三方组件。避免在对话流程未闭合前更换整个记忆底座。

每个功能切片仍以独立自然表达前后对照收口，保留首次失败。调研应给出“复用什么、适配哪里、为什么不采用其他方案”的简短结论，而不是额外制造长报告或固定选型仪式。

## 需要后续明确的边界

澄清闭环涉及新的待确认状态与跨轮状态依据，尚未实施。必须先提出存储、证据绑定、恢复和取消契约，与现有ARCHITECTURE及Provider边界核对；不能直接把历史消息重新发给状态分类模型，也不能把“是补充”独自当作完整原文证据。用户此前选择保留的隐私控制继续有效。
