# S108可审方案：分享后的两次自然接话

2026-09-28。状态：助手建议，新增用途与开发额度尚未批准；未实现或启用。依据[研究](../research/2026-09-28-share-followup-context.md)及[源码核查](../research/2026-09-28-share-followup-code-audit.md)。

## 体验目标

她主动说“这次我想把旁边空一点”，你只问“为什么这么想？”，她能接到自己刚才那句话；再问一句或重启回来，不因第一轮已标记answered便失去它。不保证任意久以前的“那个”都能找回。

## 待批准的准确增量

普通聊天规划与被选中的表达，允许向**现有DeepSeek**额外发送当前身份最近**1条已提交主动分享原文、最多400字符**，仅用来理解/回应这条话语。沿用现有历史开关；关闭时不发送。现有最近2完整用户/助手轮、4000字符保持，二者合计最多4400字符。没有新增用户历史、其他身份、私人来源或Provider；原凭据仅用于同一HTTPS鉴权。

本增量是“分享原文→普通聊天”；S107批准的是“普通聊天两轮→分享生成”，方向不同，不能视为同一许可。生活决策与主动分享生成的请求内容不增加。本轮不授权持续生活、离线补算、通知或人格自动重写。

## 选择与来源规则

1. 只从当前Admission冻结前缀中、同一canonical Timeline已验证的真实share Publication取最新1条，允许share.head_sequence等于冻结头（刚分享后立刻接话的情况）；没有分享、正常不分享、准备但未提交、失败/取消候选都不作为来源。不是从界面缓存取，也不制造user轮次。
2. 只在该share之后已有0或1个成功提交的普通聊天轮时可用，即接下来两次成功接话的窗口；失败不算成功接话，但既有失败cutoff仍优先。旧分享过期不回找更旧项。
3. `answered`只控制是否允许再开新话题，不等于用户理解/赞同，也不立即抹掉接话依据。重启按canonical顺序重新选，不能靠内存保留。
4. 本地保存share/head/event关联用于校验。Provider只得到请求内标签S1、speaker=assistant、kind=proactive-share、逐字text及与U/A的相对排列；不发送真实ID、时间戳或整条数据库记录。规划仍可不选历史，表达最多2个来源，其中可含S1，不把原文反复塞满提示。
5. 这只是“她曾这样说”的证据。不能把旧分享里猜测的房间布局或成图状态提升为事实；current_activity/current_plan/related_event继续保留独立意义。S108不扩大事件窗口，若现有事件不足以核实旧话，承认无法核实而不是回填。
6. 当前或近期控制/撤回、未知pending、完整性失败沿用原限制；分享选择需取得同一冻结前缀的cutoff，不能只凭basis.shares非空绕过。历史关闭时可继续使用原已授权当前活动，但不得恢复S1或近期对话。开关不删除记录；用户重新开启后，新的请求可读取仍在两次接话窗口内的旧分享，原已失效请求不能借重新开启复活。明确撤回/控制截止仍优先，不把开关当物理遗忘。

## 实现职责与兼容

- Timeline内部增加有界分享来源读取，复用冻结prefix与同身份验证；Runtime只传只读loader。现有RecentDialogueTurn只剩文本、已丢弃head，不能在投影阶段猜S1应该前插还是后插；v4读取时保留各完整轮本地head并与share排序，再输出局部标签及相对顺序。由ApplicationFacade仍统一承载产品入口，不引入新canonical store。
- 新版本暂名`first-life-followup-4`，保留v1/v2/v3常量、投影与已保存记录。当前v3用户窗口不静默升级；隔离验收通过后，按明确批准的v4范围通过原身份授权版本接入，保留原记录/开关。
- 可复用S107授权revision/registry锁，但须针对v4聊天补完整：出站前、阶段间、最终发布、冷恢复验证同身份/policy/history revision；关后再开也不得复用旧候选。已发出的请求无法撤回，不宣称可以。现有share_authorization只接受share/share-declined系统事件，不能直接塞到Subject聊天plan里；新增chat专属可选授权字段并绑定prepared plan，缺失/未知失败关闭，旧版省略字段保持指纹。不得把旧v3无此元数据的历史误判为v4。
- 新来源只进本能力投影，不直接进持久人物状态；当前Subject聊天收尾与原share不重写，纠错仅追加新聊天。
- 原预算grant只支持一次24→36；下一段真实验收需兼容追加授权，保留既有记录/seed/计数，不覆盖旧grant、换scope或标成普通用户调用。旧reader若遇新schema见证可能在授权追加时立即拒读，因此须在写入新授权前确认所有生活预算读取进程已支持新格式，不能等第37次开发调用后才重载。具体reader版本与恢复方案须在实施中验证后才启用新额度。

## 可观察验收

| 情景 | 必须观察到的行为 |
| --- | --- |
| 分享原文含唯一合成短语，用户仅问“为什么这么想？” | v3探针看不到该原文；v4有S1，且只从canonical来。真实回复应承接分享选择而非泛泛问卷 |
| 第一次接话后answered=true，再重启追问 | 第二次仍可取同一分享；第三次不再额外取S1，不伪报过去没分享过 |
| 聊天与分享交错、新分享出现 | 原先U/A speaker不变，相对顺序准确，最新分享替代旧项，不能同时送多条 |
| 历史关闭、关后再开、等待时切策略/身份 | 无新授权的文本不出站；已撤回的候选不发表/恢复；保留旧历史和正常其他功能 |
| 控制/未解决pending/损坏/超400字异常 | 按类型受限或FailedClosed，不伪造空历史后继续，不回找更旧分享填空 |
| 分享台词夸大、用户表示异议 | 接话能区分已说的话与已裁决活动，不把用户追问当认同，不通过改写旧台词“修复” |
| 旧v3及无分享 | 字节/恢复兼容保持；没分享也可普通聊天，不因缺S1失败 |

离线用合成Facade替身验证选择、顺序、关停和恢复；必要的新行为/既有保护检查不另造测试类别。独立复核看权限与语义，不能把结构通过数当人物自然度。

## 待批准的真实验证额度

从原200总上限内，再分配**最多8次**开发调用，累计开发上限36→44；当前总已用121，最多到129，至少留71供原额度内后续使用（其他正常用户调用会另行消耗）。不提高总额度、日6生活决策/2分享上限，不改日期或重置账本。

固定一次隔离合成情景：新开场2调用→创作决策1→分享选择1→简短追问2→重启后第二次追问2。首个正常结果不分享即停止，保留结果；任何技术失败停止，不自动重试或刷第二条。历史开关/来源污染/第三轮截止等用替身验，不额外烧真实额度。仍不能以8次小样本证明全面自然度或完整MVP。

## 后续而非本片

持续创作生活需要另定“目标为何成立、何时有真实进展、结束后如何选下一事”的有限状态与数据用途。S108优先修双方已经看到的消息接不上，避免把更多生活活动接到同一个断点上。
