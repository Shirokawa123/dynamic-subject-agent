# 角色聊天产品方向记录

最后更新：2026-09-24。状态：Q1–Q17及C19–C20已记录；五情景原型R1获初步正向反馈，后续真实对话内容仍未通过；已记录试点调用不自动提供新用途额度，完整运行机制尚未实现。

这是产品方向的连续决定记录。PRODUCT描述已确认目标，ARCHITECTURE分别说明目标结构、原型隔离与已实现基线，实际能力以代码/验收报告核实。未来体验不能被说成已经实现，文档同步也不自动授权新的数据外发或迁移。

## 为什么重新对齐

用户明确说：“主要是我不是很想体验，感觉和我想象的差距很大”。因此下一步不是要求用户先测试dogfood-s51，也不是优先升级旧身份。此前工程闭环、测试数量和本地任务保存没有证明核心聊天体验符合用户期待。

用户原始愿景（原话）：

> 我原本想象的是类似一个聊天软件一样的，就像是和网友一样交流，对面虽然是虚拟的但是很有真实感，他也有自己的生活，也会和我分享他的喜怒哀乐和他自己做的事情，然后我希望能直接导入epub之类的文本文件和直接的动漫视频文件就能分析创建人物，还有自己的原创角色也能制作。

据此确认的目标：以聊天软件为主要体验；虚拟人物有可信的性格、生活连续性和情绪来由，能分享自己做的事情；希望通过EPUB等文本、动漫视频建角，并支持原创角色。首个参照选择小说版，具体文件、技术路线和自动分析边界尚未确认。

## 已确认的决定

来源：本会话用户先说明“主要延续原作世界……但是要是能自己选择的”，随后对助手Q1–Q3建议回答“我觉得你的建议都对”。以下逐项对应，不扩展为其他未问问题的批准。

| 编号 | 决定 | 范围与含义 |
| --- | --- | --- |
| C1 | 世界模式可选，首版优先延续原作世界 | 进入新世界/不同人生也保留为后续方向；不能把原作模式做成唯一不可选路线。 |
| C2 | 用户可选择原作起始时间点 | 如某卷或某集之后；该时间点之后的剧情不自动成为角色已经历、已知的事情。具体选择界面和材料不足的处理未定。 |
| C3 | 默认保留原作世界、性格与既往经历，从起点允许分支 | 用户互动可以影响此后的选择和走向；另外提供严格遵循原剧情的模式。具体冲突规则尚未讨论。 |
| C4 | 首版中用户保持现实身份，角色生活在原作世界 | 双方通过一个双方都知道存在的聊天渠道相识，体验接近网友交流；不是默认把用户写成原作世界中的人物。渠道细节未定。 |
| C5 | 默认离线时角色生活继续推进，允许暂停或调整时间速度 | 用户对Q4回答“按照你的”。这是体验决定；后台持续运行还是打开时补算、与现实时间的具体比例尚未定。重大剧情规则现见C12。 |
| C6 | 允许主动联系及有事在忙，但控制打扰和等待 | 用户对Q5回答“按照你的”。默认可留消息，通知可关闭；不因用户未回复而反复催促。不把真实感做成频繁打扰或漫长等待。主动联系上限现见C15，忙碌时回复机制未定。 |
| C7 | 首个参照人物为《埃罗芒阿老师》的和泉纱雾 | 用户对Q6明确指定。版本见C8，起始阶段见C11；现已提供EPUB并完成本地素材清点，尚未导入运行身份或批准新的外发用途。 |
| C8 | 首个参照以小说版为准 | 用户Q7选择先用小说版，认为动画人物提取更难；该难度判断是用户选择的考虑，技术可行性仍由助手验证。替代助手先前“先以动画版为基准”的建议，不混入动画设定。现有材料见下方接收检查点，具体译本一致性仍未核实。 |
| C9 | 用户与角色从初次相识开始 | 用户同意Q8建议；熟悉、信任和交流方式从后续相处形成，不默认已有共同前史。 |
| C10 | 角色起初不预知自己是用户看过的作品人物 | 用户同意Q9建议；她把自己的世界当真实生活，只知道用户来自另一个世界。若用户后来告知看过她的故事，由角色性格与当时关系决定理解和回应，不预设立刻相信或获知所有剧情。 |
| C11 | 首个参照从小说第一卷开篇附近开始 | 用户同意Q10建议；已有背景保留，后续经历逐步展开。具体场景/段落边界须根据材料核实，不凭模型印象补写原作事实。 |
| C12 | 默认日常继续，重大节点给用户参与机会，长期缺席时停在关键节点前 | 用户同意Q11建议；另可选择世界完全自主推进，并接受可能错过事情。尚未定义重大节点、长期缺席阈值，以及关键节点等待时日常如何维持连贯。 |
| C13 | 角色有自己的意见和分享边界 | 用户同意Q12建议；可以不同意建议、拒绝话题或暂不分享，理由来自性格、经历和当前关系。不以随机对抗表现个性，也不靠责怪用户或催促回归制造存在感。 |
| C14 | 默认纯聊天消息，以自然短消息为主，也能长聊 | 用户对Q13–Q15回答“都同意”。角色通过自己的话分享生活；动作旁白作为可选模式，不默认每句话附带。语音/图片首版范围未定。 |
| C15 | 有值得分享的事情才主动联系，默认每天最多两次新话题 | 可调整或关闭；进行中的聊天不计入此上限。这是上限，不是每日必发配额；用户未回复时不连续追问。每天按哪一时钟结算、休息时段及多角色时如何合并待细化。 |
| C16 | 小说导入以自动分析、简明选择与确认为主 | 自动分析后由用户选人物、起始阶段、世界模式，并看简明设定确认；可展开来源依据、修改提取错误，高级编辑可选，不要求手填大量字段。这是产品流程决定，不表示当前已实现解析或已授权实际文件外发。 |
| C17 | 原创角色同时提供设定导入与问答辅助入口 | 用户同意Q16建议：已有完整文字设定可直接导入，只有大概想法时通过问答补充；用户提供的内容与助手建议补充的内容分开展示，确认后形成角色。 |
| C18 | 首份演示覆盖五个连续情景，以人物感、连续性和自然交流评判 | 用户同意Q17建议：选择和泉纱雾/起始阶段→初次聊天→隔天收到生活分享→接续前一天话题→角色表达一次不同意见。助手准备完整演示，用户判断感觉，不承担工程测试。预设台词、模拟时间、真正运行的能力要明确区分。 |
| C19 | 社交软件按兴趣推荐联系人，用户主动发起私信 | 用户澄清希望是随机加到网友、由系统根据兴趣爱好推荐匹配的感觉。以此取代等待正式配对/画师来信二选一；公开资料和具体开场细节仍须设计，不自动确认为原作事件或新外发授权。 |
| C20 | 修复完整自我知识及其使用机制，不能停留于表面字段 | 用户明确指出不只是笔名/作品，而是她没有关于自己的知识，并要求从第一性原则整理待办。覆盖生平、关系、能力、关注与处境等连贯认识；不等于宣称人物应全知或模型可无限补写。 |

“世界在哪里”和“剧情能否分支”是两个独立选择：原作世界内也可以产生不同剧情；不能把分支模式误记成必须进入新世界。

## 素材范围与起点的区别（2026-09-20补充）

用户指出：“只是起点可能是第一卷，实际上要补足整个人物可能需要更多内容”，并询问是否应提供全套小说、现有工程有哪些基础。此前助手仅索取第一卷/开篇材料的表述过窄，现改为区分资料覆盖范围与角色的故事起点。

- 已确认的第一卷开篇起点不意味着建角资料只能来自第一卷。可采用多卷资料；现已收到标注第1–13卷及IF的文件，但译本一致性仍需核实。
- 助手建议：多卷材料可用于交叉核对人物、世界和早期背景；每条信息需另判断事件发生时间、该角色是否知情，以及性格/关系在当时是否已经成立。后卷揭示的早期背景不应按出现卷次一概排除，也不能自动成为角色起点记忆。
- 后期成长后的性格、后续关系及尚未发生的事件，不能直接回填到开篇人物。分支开始后，原作后续也只是参考，不是运行分支里必然发生的事实。
- 本地提供文件不等于批准整本外发。实现解释见[拟议结构与复用基础](proposed-character-chat-architecture.md)，该文件是助手方案草案，不是新增用户决定或已实现功能；收到的具体材料见接收报告。

## 与当前工程的关系

### 首份原型反馈（2026-09-21）

用户原话：“对话流程上大体上是有感觉的，但是细究人物对话内容感觉不太对，感觉实际上用户和纱雾关系好像已经很接近了，而且纱雾不太会因为画杯子烦恼，毕竟按照时间线她已经画了很多年了。”

确认的评价：流程获得初步认可，人物内容和初识关系尺度未通过；不得据此关闭整个原型票。已有绘画经验应作为人物能力约束，不为制造共情桥段将其写成新手。

助手据此拟作R1修订：保留流程，收紧初识分享范围，去掉用户指导→角色依建议进步→回来回报的安排；角色继续自己的专业工作，双方仅围绕已有话题交流。具体新台词仍是待评价草稿，不是用户已经认可的新人物结论。

用户随后评价R1“感觉还行”，并询问如何分析判断人物主体。记录为R1的初步正向反馈，可作为下一阶段设计的输入；不扩大为全人物还原、真实模型聊天或生活引擎已经通过。原型票以有限体验探索收口。

本次实际方法：只核对第一卷开篇与章内少量明确回忆的先前背景，人工归纳约束、手写情景台词，再根据用户反馈修订。没有对全套小说作人物语义分析、训练模型或调用DeepSeek。原型运行的是预设情景状态转换，不是人物动机驱动的新行为生成。

助手后续建议（未实施）：分别核对身份/能力/知情、在意的事情与目标、对象和关系阶段、当时处境、表达方式。将明确原文、跨场景归纳和待核实推断分开；语言习惯不能替代动机与自主选择。初版的问题说明人工编情景也会越过经验/关系约束，不能将助手判断本身当作事实。

dogfood-s51是可复用的身份、记忆、状态和可靠持久化基础，不是此愿景已经完成的证据。旧文档中生活模拟/主动消息等冻结项与新愿景存在待解决的产品范围差异；当前仅进行需求设计，不越过旧授权直接实施。不可逆迁移、新credential用途、新Provider数据用途仍需具体授权。

用户随后追问是否应先对旧软件做方向重构。已补入[方向与架构对齐评估](character-chat-architecture-alignment.md)，作为原型前置研究：它区分保留基础、重组聊天和新增生活/分享职责，并列出需要同步的旧契约。该报告是助手建议，不新增用户已确认决定，也不是正式重构已完成。
