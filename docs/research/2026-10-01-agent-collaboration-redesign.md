# 开发 Agent 分工重构依据

2026-10-01。用户要求取消现有模型限制，调研并重构开发分工。结论：保留主窗口对完整结果负责，按任务依赖临时组织实施、调查和复核；模型与思考档按当次任务选择，不绑定岗位、不设置项目级上限。收益仍需实际工作验证。

## 已有能力与已证实缺口

本次基准为`2a080b2`。原[协作策略](https://github.com/Shirokawa123/dynamic-subject-agent/blob/2a080b2/docs/plans/agent-execution-strategy.md)已有短上下文、写入归属、独立复核、总消耗和停止重复验证等机制，可继续使用。缺口是默认岗位固定为Astra主控、Luna调查/简单实现、Sol实施/复核，AGENTS还把Sol限制为最高xhigh；这与用户本次要求冲突，且仓库没有任务级对照证据证明这些固定搭配最优。

原文还混有上游安装细节、价格缓存和历史试验记录，执行时很难区分当下规则与过往依据。仓库未发现`.codex`目录，本轮没有项目级角色配置可同步修改；未检查或改动用户全局配置，不宣称全局没有模型绑定。

用户结果是模型选择有充分空间、协作能推进完整体验。可观察验收：AGENTS入口与策略一致；不再有当前有效的固定模型岗位或Sol档位上限；直接做、并行、独立复核各有适用条件；后续能用产物、返工与体验证据判断策略收益。当前仍属S109开发方式调整，不启动产品实现或48次模型实验。

## 采用与不采用

采用按任务组织团队：主窗口维护整体目标、当前假设和接纳；需要时设置一个完整结果的实施所有者；独立调查和高风险复核按实际依赖加入。这是结合文献与仓库情况作出的设计选择，不是论文保证。

| 候选办法 | 取舍理由 |
| --- | --- |
| 所有工作都用最高档、固定大团队 | 不采用为默认；没有证据证明可弥补缺失上下文或串行依赖，允许具体困难任务直接用高能力模型/深思考 |
| 先用最便宜模型，失败后逐级升级 | 不采用为固定流程；高后果、难验证任务可直接选择更可靠组合，避免故意支付试错成本 |
| 固定探索→实施→审查流水线 | 不采用为必经程序；已有证据足够就直接实施，简单工作可自行完成必要检查 |
| 多模型投票或审查问题配额 | 不采用为完成标准；不同模型也可能重复同一误解，要求可复核证据和反例 |
| 新编排框架或全局角色profile | 暂不引入；现有工具已能覆盖任务、上下文、模型和回收，不增加配置优先级与维护负担 |

模型选择先看任务难点、错误后果、可验证性和已有实际表现，再兼顾耗时与总消耗。任何可用模型均可承担调查、实施或复核；同模型的新上下文复核也可采用。遇到失败先区分资料不足、工具限制、规格冲突和推理困难，再决定补资料、收拢任务、换模型或调档。

这次是软件开发协作，心理学/哲学不直接决定模型分工，因此不引入人格、动机或意识理论。使用的是任务结构和多Agent实证/工程资料，不能把角色名称当作人类团队心理机制已在模型中成立。

## 怎样验证是否改善

文档验收检查有效规则与导航、相对链接、历史替代说明，以及是否仍暗含固定模型岗位、必须派人、固定人数或必须反复审核。用三种桌面推演核对：简单文档直接完成；独立调查可并行且主窗口不重做；共享状态实现由一个所有者贯通，稳定差异按风险独立复核。推演只能验证规则可执行，不能证明生产效果。

在后续正常授权任务的既有收尾中简记团队选择及理由、完成时间、可得模型/档位与用量、返工原因、真实缺陷和用户结果。拿不到的数据记未知，不为统计扫描无关日志、不重复实现同一功能做昂贵基准。协调/合并/返工超过收益时收拢团队；独立任务长时间排队时增加并行；正确性瓶颈才增加针对性复核或提高模型能力。观察不足时不承诺节省比例。

本轮有一项独立只读研究与主窗口的官方能力核查并行，未发生共同写入。它证明当前工具可执行这种分工；长期成本、质量和人物产品收益仍待实际任务观察。
