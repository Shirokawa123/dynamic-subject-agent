# S108 主动分享接话：有界源码核查

2026-09-28。仅核对仓库源码、契约和合成测试；未读取用户私聊或 `.local` 运行数据，未调用 Provider、凭据或启动服务。本文件区分源码已证实的行为与待验证的改动方案。范围依据 `docs/slices/current.md`、`docs/slices/slice-108-share-followup-context.md` 和 `docs/ARCHITECTURE.md:7-45`。

## 已证实的现状

1. **分享原文是 canonical，但不是聊天轮次。** `LifeRecord` 的 `kind=share` 必须有 `share_id/disclosed_event_id/share_text`（`src/dynamic_subject_agent/first_life.py:316-337`）；发布前还核对分享正文等于表达正文（`src/dynamic_subject_agent/timeline.py:4446-4458`）。schema3 的 `life_record` 与 publication 一起写入（`timeline.py:5799-5812`）。`first_life_basis` 先核全链，再重放成 `LifeShare(share_id, head_sequence, event_id, revision, text, language, answered)`（`timeline.py:4381-4405,4467-4501`）。`list_first_life` 暴露 shares（`timeline.py:4525-4530`），Facade 查询和桌面 Adapter 把它们与对话按 `head_sequence` 合并，页面明确渲染“主动分享”（`src/dynamic_subject_agent/application.py:932-945`；`app/desktop/first_life.py:36-63`；`app/desktop/static/first_life.html:21-25`）。界面可见因此有源码依据，但不等于模型已收到原文。
2. **v3 聊天规划与表达确实漏掉主动分享原话。** `list_conversation_turns` 在生活分支只选 `SubjectCommand`，跳过 `FirstLifeInput`（`timeline.py:7214-7236`）。冻结上下文把 `character_dialogue_before` 装给 cognition（`src/dynamic_subject_agent/runtime.py:1067-1088`）；`FirstLifeCognition._chat` 只加载这份 dialogue，选择 v3 `life_chat_planning` / `life_chat_expression`（`src/dynamic_subject_agent/first_life_cognition.py:167-191`）。v3 从最多两轮的 `recent_dialogue` 生成 U1/A1/U2/A2，并仅把规划选中的最多2项原文送表达（`src/dynamic_subject_agent/first_life_grounded.py:88-141`）。`current_activity/current_plan/related_event` 是创作状态及事件摘要／差异，不含分享台词（`src/dynamic_subject_agent/first_life_projection.py:55-75`；`src/dynamic_subject_agent/first_life_relevance.py:168-175`）。所以在“分享后第一句只说‘你刚才说的那个’”且没有重新贴出分享内容时，**模型看不到该分享原话**；它可能看到项目状态和一个事件，但不能由此逐字知道她说了什么。零Provider合成探针以 `.venv/bin/python.exe -` 从标准输入运行，复用 `tests/test_first_life_relevance_projection.py:19-43` 的纯合成 fixture，把唯一短语放入 `LifeShare.text`，断言短语存在于 share，而在 v3 planning/expression 投影及两阶段 wire 均不存在；输出为 `zero-provider synthetic: share present in LifeShare; absent from v3 planning/expression payload and wire`。它只验证投影缺口，不验证真实回复质量。
3. **分享的 `answered` 是生活节奏标记，不是历史读取权限或精确指代判定。** 每次成功发布 `SubjectCommand` 都将此前所有 shares 标成 `answered=True`，不检查是否谈及分享（`timeline.py:4486-4501`）；重启时从 canonical publications 重新计算，原分享正文与 head 仍在。`unanswered_share` 抑制新主动联系（`timeline.py:4478-4479,4521-4522`；`src/dynamic_subject_agent/first_life_cognition.py:142-144`），而 `query_first_life().shares` 仍返回已回答项。现有合成验收证明未回答分享在重启后可读、下一成功聊天后变已回答（`tests/test_first_life_facade.py:96-126`），但没有证明该聊天实际取得了分享原文。以 `answered=False` 作为接话窗口条件，会在用户第一句回应后过早截断第二句追问。
4. **现有授权只覆盖 user/assistant 完整轮次。** S104 聊天最多2完整轮/4000字符，分享本来不进窗口（`docs/ARCHITECTURE.md:25-27,39-45`）。S107 授权扩展的是主动分享任务读取同身份最多2完整 committed `{user_text, assistant_text}`、合计4000字符，受历史开关控制；v3 对话来源也只从这两轮派生（`docs/ARCHITECTURE.md:13-21`）。v2 分享投影含 `recent_dialogue`（`src/dynamic_subject_agent/first_life_relevance.py:197-212`），v3 的生活决策/分享 wire 委托 v2 保持原字节（`src/dynamic_subject_agent/first_life_grounded_provider.py:15-18`）；这些都没有授权把 **assistant-origin share 原文** 增加到后续聊天 Provider 投影。新 S1 外发字段即使只取同一身份、同一 DeepSeek，也属于新增用途，须在实际外发前取得精确批准。现有历史开关 `history_revision` 和 share guard 只保证 S107 分享任务撤回（`src/dynamic_subject_agent/local_identity_authority.py:1289-1330`；`docs/ARCHITECTURE.md:19-21`），不能直接宣称普通聊天也有同级竞态保证。

## 可复用接缝与最小可实现方案（待授权、未实现）

沿既有单条 `first-life-grounded-3` 分支开**显式新 runtime policy 版本**，不改 v1/v2/v3 wire。复用 `LifeShare` 的 canonical `head_sequence/text/answered`、`first_life_basis(expected_head=...)` 的全链与冻结头检查、`character_dialogue_before` 的完整轮/控制检查，以及 v3 的请求内来源引用和表达精确拷贝。新 chat-only reader 从同一冻结全局前缀选最近**1条已提交主动分享**，要求 `share.head_sequence <= expected_head` 且早于当前未提交聊天结果；分享后立刻接话时二者相等。正文最多400字符。候选条件建议为其后、当前请求前成功发布的 `SubjectCommand` 数量小于2，因此第一和第二次成功聊天能承接；失败/中断聊天不消耗此语义窗口，`answered` 不作截断。两轮 U/A 仍各完整、合计最多4000字符；S1 是另外最多400字符，总外发文本上限4400。v4 规划可看 S1 与两轮 U/A；规划只可选择最多2个来源，表达由 Python 原样复制被选中的 S1/U/A，S1 的 `speaker=assistant` 与 `origin=proactive-share` 明示“她曾这样说”，不得伪装成用户输入、事实权威或原作经历。`related_event` 仍按现有 `use_life` 单独裁决：分享说过的话不自动证明创作方案、现实场景或图片已经存在。

现有 `_validate_sources` 只接受 U1/A1/U2/A2 且要求完整成对（`src/dynamic_subject_agent/first_life_grounded.py:88-102`），不能把 S1 塞进 `dialogue_sources` 或伪造一轮 `RecentDialogueTurn`。最小 seam 是：在 runtime/Timeline 增一个只读、冻结头的 share-followup 选择器；`CognitionView` 只为 v4 chat 增 loader；新投影、校验、adapter 允许独立 S1 来源，保持原 v3 类型/adapter 拒绝该形状；`local_identity_authority` 的 policy digest/version 显式登记并精确启用。不要新建 canonical store 或把分享复制进 chat history。原 share 任务与 life-decision 仍委托现有 wire。合成用例应逐字比较旧 v3 和新分支这两类任务的 outbound bytes。

交错顺序还需要一个本地字段：`ConversationTurnRecord` 有 `head_sequence`（`timeline.py:7230-7235`），但 `select_recent_dialogue` 转为 `RecentDialogueTurn(user_text, assistant_text)` 后丢掉它（`src/dynamic_subject_agent/recent_dialogue.py:16-20,119-136`）。要实现方案承诺的分享与 U/A 相对顺序，v4 reader 必须在同一冻结前缀保留各轮的本地 head，先排序再只外发请求内标签/顺序；不能凭现有 U1/A1/U2/A2 标签推断 S1 插入位置。该 head 不进入 Provider。

**截止与失败语义须补齐后才能实施。** `character_dialogue_before` 通过 attempt basis 验冻结头，未决/未冻结或控制意图不明的 admission 会返回不可用，并以 `cutoff` 切除更早对话（`timeline.py:7501-7519,7539-7581`）；`select_recent_dialogue` 在控制、Memory 状态或超长处停止（`src/dynamic_subject_agent/recent_dialogue.py:119-136`）。S1 读取必须受相同或更严格的截止约束：当前控制请求、最近有效控制边界、未决更正/撤回或来源完整性未知时，**不带 S1 外发**；不能因 S1 reader 返回空就绕过原 dialogue 的 FailedClosed。确定的历史关闭只发经核验的无 S1 请求；canonical/权限读取失败应 FailedClosed，不把未知伪装成空。关闭后再开启允许**新请求**在尚未过两轮窗口时重新选择旧 share，与“关闭不删除本地记录”一致；但关闭前准备的**旧请求候选**须因 `history_revision` 改变而失效（`src/dynamic_subject_agent/local_identity_authority.py:1321-1330`），即使开关再次变成 true 也不能发表。

表达前至少复核历史开关／版本；当前普通聊天已有规划后 bool 复核（`first_life_cognition.py:188-191`），但同值关闭再开启会绕过单一 bool 比较。新用途若承诺 S107 式撤回，就应绑定 `history_revision`/runtime policy revision、发送时与 publication 前的 guard，并在重启 prepared plan 回放时重验；否则要在方案和批准中明确较弱的保证。现有冷恢复只重放完整 prepared plan、不重新调用模型（`src/dynamic_subject_agent/runtime.py:1125-1145`）；新增读取不能在重启时拿“当前最新分享”给旧 frozen attempt，且 policy 回退不得让旧 plan 当作 v4 继续外发。

建议最小合成验收：① share→首次简短追问，规划含精确 S1，表达仅在选 S1 时含逐字 S1；② 再一轮追问可用，第三轮不可用，失败轮不计数；③ 首次追问后 `answered=True` 和冷重启后仍按同一 head 窗口选择；④ history off、明确控制/撤回、未决 admission、坏 canonical 链或损坏 authority 分别零 S1／FailedClosed；⑤ 新旧 adapter 互拒错误版本，v1/v2/v3 与 life/share wire 不变；⑥ S1 只标“本人已说的话”，不能将 S1 中未经证实的成图/现实物件当事实。效果验收另用“你刚才说的那个”“那留白呢”两句，检查具体承接且不编造已经成图；结构通过不等于自然交流通过。

## 开发额度兼容核查

现有 `FirstLifeBudget` 只有固定 S107 `DEVELOPMENT_EXTENSION_ID`，原 life chain seed 仍为24，`PRAGMA user_version=1` 与单例 `life_development_grant` 同时存在才承认 grant；body 精确绑定原 config、grant 时 life 前缀和累计24→36，返回上限36（`src/dynamic_subject_agent/first_life_budget.py:12-13,37-39,60-115`）。`claim_life` 在同一事务按此上限计费，总200及日6/2另行检查（`first_life_budget.py:131-152`）。现有合成测试覆盖批准幂等、坏 grant、旧 reader 等边界（`tests/test_first_life_budget_extension.py:85-149,193-218`）。故 36→44 既**没有现成 grant 参数**，也没有用户本轮授权；将旧 `limit=36` 常量改44会使既有 body/digest与旧数据库失配。

若以后获批36→44，应另增唯一授权ID与第二段追加 grant，保留原24 seed、S107 grant、原 stage/life 记录和原 scope 中的 `development_call_limit=24` 字段；新 reader 先核旧24→36 grant，再核授予时不可变前缀中开发已用≤36、目标累计44，最后同事务比较 claim。需要显式 schema 见证/迁移兼容测试、重复授权幂等、损坏与中断失败关闭。**必须在写入新 grant 前重载所有会读取此账的生活预算进程**：若沿用 `user_version` 并改为2，旧 S107 reader 会在 grant 追加时立即因版本不等于1而失败；即使用旧版可忽略的新见证设计，超过36的 claim 后它也会失败。准确兼容窗口取决于新 schema，不应预先承诺。旧 `CharacterChatBudget` 的全局账读取兼容也要以合成测试确认。额度扩展与 S1 新数据用途是两个独立批准对象，不能互相推导。
