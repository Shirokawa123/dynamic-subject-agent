# Slice-30：记忆回答与可用记录一致

状态：in progress。基线 `fb28c36` / `dogfood-s29`，用户明确要求继续已提出的 Slice-30。

## 用户结果

有明确可用记忆时据记录回答；记录不可用时只说明无法确定，不推断事件未发生或未安排。区分候选选择、reply 输入与最终表达失败，不将要求用户重新确认已经记录的内容视作成功。

## 范围与边界

- 先用 Slice-29 head89/head94 的真实失败建立 ApplicationFacade 对照，保留首次失败；不按两句台词新增过滤特例。
- 形成有具体输入/输出和回退语义的机制方案，再改代码。若需调整既有 Memory reply 结构或提示，在报告中先明确精确契约；不扩大 Provider 数据字段、用途、历史窗口或调用预算。新数据用途或统一表达架构另行请求授权。
- 保持模型提议/Python 裁决、单 Timeline/原子提交、六能力隔离；普通聊天、创作、Knowledge 原文、目标与关系独立结果不因 Memory 回答变化失效。
- 更正与遗忘不恢复旧内容；现有请求/披露不确定时不猜空库存、不猜未安排。正式身份、旧救援数据和凭据均不操作；沿用已授权合成林柚隔离根与 DeepSeek 用途做后台 HTTP 验收。

## 验收与收口

1. 正确选中、空选择、错误选择、Provider/历史失败分别可观测；选中数量不能冒充选中对象证据。
2. 原场景与未参与设计的改述、无关话题、更正/遗忘与重启均检查；成功、诚实未知与失败分别报告。
3. 既有 Interface 回归、全量测试、独立规范/需求两轴 code-review；STATUS 更新不超过五行，任务书与报告收口，commit 并 push 已配置远端。
